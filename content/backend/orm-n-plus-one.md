# ORM과 N+1 문제

ORM 은 테이블의 행을 객체로 바꿔준다. 편해지는 대신 **어떤 SQL 이 나가는지 코드에서 보이지 않게** 된다. 성능 문제는 거의 항상 그 틈에서 나온다.

## N+1

주문 목록을 가져온 뒤 각 주문의 회원을 참조하면, 목록 쿼리 1번에 회원 조회 N 번이 따라붙는다.

```java
List<Order> orders = orderRepository.findAll();   // 쿼리 1번
for (Order o : orders) {
    System.out.println(o.getMember().getName());  // 주문 수만큼 추가 쿼리
}
```

목록이 10건일 때는 보이지 않다가 10,000건이 되는 순간 장애가 된다. 해법은 필요한 것을 **한 번에** 가져오는 것이다.

- `join fetch` 로 조인해서 한 쿼리로 받는다.
- 컬렉션이 여러 개라 조인이 폭발하면, 대신 `IN` 절로 묶어 받는다(배치 조회).

## 지연 로딩을 기본으로 둔다

즉시 로딩을 기본으로 하면 쓰지도 않을 연관 객체까지 매번 따라온다. 기본은 지연 로딩으로 두고, 필요한 화면에서만 명시적으로 함께 조회하는 편이 예측 가능하다.

## 결국 SQL 을 봐야 한다

실행되는 쿼리를 로그로 찍어 확인하지 않으면 ORM 은 블랙박스다. 느린 쿼리가 보이면 그다음은 ORM 이 아니라 DB 문제다.

## 연결

- 조인과 조건절이 타야 할 대상이 [[인덱스]]다.
- 조회 하나가 아니라 작업 단위로 커밋 범위를 잡는 문제는 [[트랜잭션]]이다.
- 조인이 많아지는 근본 원인은 [[정규화]]로 테이블을 쪼갰기 때문이며, 그래서 읽기 위주 화면은 일부러 역정규화하기도 한다.
- 쿼리가 N 배로 늘면 [[커넥션 풀]]을 그만큼 오래 붙잡는다.
