# REST API 설계

URI 는 **자원**을 가리키고, 무엇을 할지는 [[HTTP]] 메서드가 말한다. `POST /getUser` 처럼 URI 에 동사를 넣으면 그 규약이 깨진다.

## 멱등성

같은 요청을 여러 번 보내도 결과가 같은 성질이다. 네트워크는 응답을 잃어버리므로 클라이언트는 재시도를 하고, 그래서 멱등성은 이론이 아니라 장애 대응 수단이다.

| 메서드 | 멱등 | 안전 |
| --- | --- | --- |
| GET | O | O |
| PUT / DELETE | O | X |
| POST | X | X |

`POST` 로 결제를 만드는 API 는 클라이언트가 만든 키(`Idempotency-Key`)를 받아 중복 요청을 걸러내야 한다.

## 상태 코드를 골라 쓴다

- 요청이 문법은 맞지만 업무 규칙에 걸리면 `422`, 권한이 없으면 `403`, 인증이 없으면 `401` 이다.
- 오류를 전부 `200` 에 담아 `{"success": false}` 로 내려보내면 중간 계층이 아무것도 판단할 수 없다.

## 목록은 반드시 자른다

전체 조회는 데이터가 늘면 그대로 장애가 된다. `offset` 페이지네이션은 뒤로 갈수록 느려지므로, 정렬 키를 커서로 쓰는 방식이 안전하다. 정렬 키에는 [[인덱스]]가 있어야 한다.

## 연결

- 무상태를 유지해야 서버를 늘릴 수 있고, 그 성질을 [[로드 밸런싱]]이 활용한다.
- `GET` 응답에 캐시 헤더를 붙이는 순간 [[캐싱 전략]]의 무효화 문제가 그대로 따라온다.
- 누가 요청했는지 판단하는 부분은 [[인증과 인가]]가 맡는다.
