# 커넥션 풀

DB 연결 하나를 만드는 데는 TCP 핸드셰이크와 인증이 필요하다. 요청마다 새로 맺으면 질의보다 연결에 시간을 더 쓰게 되므로, 미리 만들어 두고 빌려줬다 돌려받는다.

## 풀 크기는 작을수록 빠를 수 있다

풀을 키우면 동시에 일하는 [[스레드]]가 늘어나지만, DB 서버의 코어와 디스크는 그대로다. 일꾼이 자원보다 많아지면 그때부터는 일이 아니라 [[컨텍스트 스위칭]]과 잠금 경합이 늘어난다. 그래서 처리량 곡선은 어느 지점부터 **떨어진다**.

응답이 느려질 때 풀 크기를 올리는 것은 대개 반대 방향의 처방이다. 먼저 커넥션을 오래 붙잡는 쿼리를 찾아야 한다.

## 고갈은 항상 다른 문제의 증상이다

풀이 비어 요청이 대기하는 상황은 원인이 따로 있다.

- 트랜잭션 안에서 외부 API 를 호출해 커넥션을 붙잡은 채 네트워크를 기다린다.
- 예외 경로에서 커넥션을 반납하지 않는다.
- 한 요청이 커넥션을 두 개 필요로 하는데 풀이 그보다 작다 — 서로 상대가 반납하기를 기다리는 [[데드락]]이 된다.

## 타임아웃을 반드시 준다

대기 시간에 상한이 없으면 느려진 DB 하나가 앞단 스레드를 전부 붙잡아 서비스 전체가 멈춘다. 빌리는 시간, 질의 시간, 유휴 연결 수명에 모두 상한을 둔다.

## 연결

- 커넥션을 언제 빌리고 언제 놓을지는 [[트랜잭션]]의 시작과 끝이 결정한다.
- 쿼리 수를 늘려 커넥션을 오래 쥐게 만드는 대표적인 원인이 [[ORM과 N+1 문제]]다.
- 앞단에서 요청을 여러 서버로 나눠도 DB 커넥션 총합은 그대로이므로, [[로드 밸런싱]]으로 서버를 늘릴 때 풀 크기를 함께 계산해야 한다.
