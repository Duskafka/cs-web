# 마이크로서비스 아키텍처

하나의 큰 애플리케이션 대신, 독립적으로 배포·확장·장애 격리되는 작은 서비스들로 나눈다.

## 얻는 것과 잃는 것

| 얻는 것 | 잃는 것 |
| --- | --- |
| 독립 배포와 팀 자율성 | 네트워크 호출의 지연과 실패 |
| 서비스별 기술 선택 | 분산 트랜잭션의 어려움 |
| 부분 확장 | 운영·관측 복잡도 |

## 데이터가 진짜 어려운 부분

서비스마다 데이터베이스를 따로 가져야 진짜 독립인데, 그러면 조인이 사라지고 일관성은 최종 일관성이 된다. 여러 서비스를 거치는 작업은 2PC 대신 **Saga** 로 보상 트랜잭션을 엮는다. 이 모든 것이 CAP 정리가 말한 절충의 실제 모습이다.

## 연결

- 서비스 간 결합을 낮추려면 동기 호출 대신 메시지 큐를 쓴다.
- 요청 라우팅과 API 게이트웨이는 로드 밸런싱의 L7 기능으로 구현한다.
- 서비스별 데이터 분리는 샤딩과는 다른 축의 분할이다.
