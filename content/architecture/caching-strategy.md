# 캐싱 전략

## 읽기 패턴

- **Cache-Aside**: 앱이 캐시를 먼저 보고 없으면 DB 에서 읽어 채운다. 가장 흔하다.
- **Read-Through**: 캐시 계층이 직접 DB 를 읽어온다.

## 쓰기 패턴

- **Write-Through**: 캐시와 DB 에 동시에 쓴다. 일관성은 좋고 쓰기는 느리다.
- **Write-Back**: 캐시에만 쓰고 나중에 DB 로 내린다. 빠르지만 장애 시 유실 위험이 있다.

## 축출 정책

LRU, LFU, TTL. 무엇을 버릴지 고르는 이 문제는 [[가상 메모리]]의 페이지 교체 알고리즘과 완전히 같은 문제다.

## 어려운 것들

- **Thundering herd**: 인기 키가 동시에 만료되면 요청이 한꺼번에 DB 를 때린다. TTL 에 지터를 주거나 락으로 한 요청만 갱신하게 한다.
- **무효화**: 원본이 바뀌었을 때 캐시를 언제 지울지는 여전히 어렵다. [[정규화]]를 되돌릴 때 생기는 중복 갱신 문제와 성격이 같다.

## 연결

- 클라이언트 쪽 대응물이 [[브라우저 캐시]]다.
- 캐시 키를 노드에 분산할 때 일관된 해싱을 쓰며, 기반은 [[해시 테이블]]이다.
- 계산 결과를 재사용한다는 점에서 [[동적 계획법]]의 메모이제이션과 발상이 같다.
